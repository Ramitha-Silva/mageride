## Scope
Walking-skeleton slice 3 of 6. The happy path of the Mode C ride aggregate only:
Requested -> Matching -> Offered -> Accepted -> DriverArrived -> InProgress -> Completed ->
PaymentPending, with the atomic accept and the outbox already correct. Plus a fare stub that
returns a flat estimate so the flow can complete. ADD: [R-01, R-02, R-14, R-18, E-09].

**Fences — do not cross these:**
- ride-svc != trip-state-svc. Mode A/B sessions are NOT in scope, now or ever (R-01).
- No cancellation matrix, no no-show, no proxy, no package, no durable Quartz timers — C032/C037.
- The fare stub is explicitly temporary and must be replaced by C049/C050; mark it so in code.

## Deliverables
- backend/src/Ride.Api — POST /v1/rides/request, GET /v1/rides/{id}, offer accept/decline, arrive, start, complete
- atomic single-winner accept — conditional UPDATE on (state, offer_expires_at, version) per §11.11
- rides.command_log idempotency replay + rides.outbox writes with LISTEN/NOTIFY dispatch
- backend/src/Fare.Api (stub) — GET /v1/fare/estimate returning a flat spec-shaped estimate
- backend/src/Ride.Api.Tests incl. a concurrent-accept test

## Definition of Done
- one booked ride walks the full happy path and lands in PaymentPending
- two drivers accepting the same offer concurrently produce exactly one 200 and one 409
- replaying POST /rides/request with the same clientRequestId returns the existing ride (R-18)
- ride.* events reach Redpanda through the outbox, never by direct publish
