## Scope
The versioned GTFS feed lifecycle behind SCR-AP-016: upload, async validation with a row-level
error report, preview, atomic activation, version history and one-click rollback.
ADD: [AL-54, AL-55, AL-56, D-35].

**Fences — do not cross these:**
- The GTFS dataset is an EXTERNALLY PROVIDED file — launch feed and every refresh. There is no in-house authoring workstream (AL-56).
- Activation is one transaction. A failed activation leaves the previous feed live, untouched.
- Exactly one feed row may be `active` — enforced by the partial unique index, not by application logic alone.

## Deliverables
- POST /admin/transit/gtfs/uploads (multipart zip <= 200 MB, sha256 dedupe -> 409, 413 too large) -> 202 {feedVersionId}
- async validation pipeline — referential integrity, duplicate IDs, Sri Lanka bbox check, service-window sanity, stable-ID warnings
- GET uploads/{id} status + counts + feedInfoVersion + service range + first-5 error summary; GET .../report (JSON/CSV)
- POST uploads/{id}/activate — load transit_staging.gtfs_*, single-transaction swap, NOTIFY transit_feed_activated (Idempotency-Key)
- GET versions (history) + versions/{id}/download (signed URL); rollback = activate on an archived validated version
- original zips retained in object storage >= 12 months; every mutation audited (D-35)

## Definition of Done
- a malformed feed fails validation and produces a downloadable row-level report; nothing is activated
- activation swaps live tables atomically and transit-svc serves the new routes within 60 s
- re-uploading the identical file returns 409 with the existing version number
- re-activating an archived version restores it and archives the current one
