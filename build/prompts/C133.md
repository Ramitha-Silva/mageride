## Scope
The weekly driver payout run — the discharge of the custody AL-57 created. A card-paid ride
moves passenger wallet -> driver wallet, so the driver's balance is money MageRide OWES; AL-05
had deleted the only outward bank rail. This service is that rail and nothing else: it prices
nothing, settles no ride, and never decides who may be paid.
ADD: [AL-57, AL-58, D-09, D-38, R-19].

**Fences — do not cross these:**
- Weekly FULL sweep — no minimum and no holdback. Whatever the balance is on run day is paid in full (Payout:RetainMinor defaults to 0).
- The wallet debit and the payout instruction commit TOGETHER. An instruction with no debit pays twice on a retry; a debit with no instruction loses the driver's money.
- A driver with no VERIFIED payout profile accrues and is never swept. The balance is retained, never lost, and they surface on the Finance exception queue.
- This service writes NO ledger row itself — every movement goes through wallet-svc's internal plane, as C060 does (D-09).
- The bank adapter is ONE outbound port and no provider is chosen. Unconfigured, the run still selects, still debits and still records what is owed, and announces the gap at start-up.

## Deliverables
- billing.payout_batches + billing.payouts, and the driver_payout journal kind (AL-58)
- the scheduled weekly run — select drivers with a verified profile and a positive balance, debit, raise an instruction
- GET /v1/drivers/payouts (SCR-DA-022a) and GET /v1/admin/payouts + /batches (SCR-AP-006)
- POST /v1/admin/payouts/batches — run out of band, idempotent on the Colombo business date (409 payout-batch-exists)
- POST /v1/admin/payouts/{id}/retry for a FAILED instruction, and the internal result callback deduped on provider_reference (R-19)
- FAILED reverses the debit under the same idempotency-key discipline, exactly once, and the next run picks the balance up again

## Definition of Done
- a sweep debits each eligible driver's whole balance and raises exactly one instruction, in one transaction each
- a driver with no verified payout profile is skipped and keeps every rupee
- a redelivered bank result neither pays twice nor reverses twice
- a FAILED instruction restores the balance exactly once and the following run sweeps it again
- running the sweep twice for one Colombo date is a 409, not a second set of instructions
- with no bank adapter configured the run still records what is owed and says so at start-up
